# 性能基准（清单 36）

量的是「卡片多起来之后，画布还顺不顺」。固定 30 / 100 / 300 张三档，
每档量四件事：

| 指标 | 怎么看 |
| --- | --- |
| 打开耗时 | 从导航到卡片进入 DOM（`readyMs`）；含首屏绘制的看 `paintedMs` |
| 平移 / 缩放帧率 | 连续派发 wheel + pointermove，用 rAF 统计帧间隔；`fps` 越大越顺，`p95Ms` 越小越稳 |
| 改卡片参数 | 点开卡片再收起，走展开 / 参数区重建这条最重的路径，5 轮取平均 |
| 展开面板 | 点开卡片到 `.node-panel` 真的进 DOM |

## 跑

```bash
# 三档全跑
runtime/node.exe tools/bench/run.js

# 只跑 30 张（改代码时快速看一眼）
runtime/node.exe tools/bench/run.js --sizes=30

# 跑指定几档
runtime/node.exe tools/bench/run.js --sizes=30,100
```

结果写到 `tools/bench/result-<日期>.json`，同一天重复跑会覆盖。
需要本机有 Chrome（无头模式）。数据目录用临时副本 + 独立端口（17995），
**不会碰真实 `data/canvas.db`**。

## 怎么用

这个脚本的价值在**对比**，不在绝对值：

1. 动手改渲染相关代码之前，先跑一次，留住当天那份 `result-*.json`；
2. 改完再跑一次，对比同一档位的数字；
3. 明显变差就是回退了，别急着提交。

注意事项：

- **只在同一台机器上比。** 不同机器的 CPU / Chrome 版本差异比这里要量出的
  改动收益大得多，跨机器数值没有可比性。
- 无头模式的帧率上限就是 60fps，30 / 100 张三档通常都贴着上限，
  看不出差距属于正常——真正能拉开差距的是 300 张那一档
  （实测 300 张时 p95 帧间隔会明显抬高）。
- 单次测量会被 GC 与后台任务抖动影响，只看趋势，别揪着几毫秒的差异。

| --- | --- | --- | --- | --- | --- | --- |

### 与 2026-11-03 基线对比（同一台机器）

| 档位 | 打开（ready） | 绘制完成 | 改参数 | 展开 |
| --- | --- | --- | --- | --- |
| 30 张 | 128 → 119.5ms | 175 → 160.8ms | 11.6 → 15.6ms | 2.2 → 3.0ms |
| 100 张 | 96 → 70.6ms | 174 → 151.3ms | 3.3 → 4.7ms | 3.0 → 4.1ms |
| 300 张 | 179 → 88.7ms | 360 → 286.1ms | 7.6 → 5.2ms | 9.9 → 6.9ms |

本轮（2026-11-04）主要改动：

1. `computeSnap` 去掉每轮重复计算的 `selfBounds` / 对齐候选数组，内层只做算术比较；
2. `paintScheduleState` 由「多次 filter / find / sort + 每个成员再 find」改成一次遍历 + `Map`；
3. `applyViewport` 给 `transform` / `background-position` 加值比较，值没变就不写样式；
4. `renderNodes` 不再让视口缓存失效，改成建卡前 `primeViewportBox()` 预量一次；
5. 小地图主题色 `getComputedStyle` 结果缓存 + 建卡前预热，消除建完 300 张卡后的整篇样式重算；
6. 工具栏溢出 / 压小地图 Bug 修复：`max-height` 不再被 `Math.max(pill, ...)` 撑出屏幕，
   极矮窗口自动降级到两列 / 三列，实在放不下才临时盖住小地图（并让小地图淡出）。

300 张这一档的 p95 帧间隔仍是 16.8 → 33.4ms，说明「卡片数量上去之后拖动 / 缩放
开始掉帧」的根因还在（每张卡片有伪元素描边 + 流光动画，合成层太多），
这也是后续卡片局部更新 / 特效降级要继续啃的地方。
